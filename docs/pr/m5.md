# M5: Start, booking, brief, waitlist, analytics

## What changed

### Start (`/start`)

- The board's page: the headline and lead, the booking card, the four-step brief, and "What happens next".
- **Booking card:**
  - ten weekdays and four times a day, from `/api/slots`, shown in the visitor's own time zone ("Times shown in CET", WAT for Lagos)
  - an email, then "Confirm Thu 23 Oct, 10:00"
  - the booked state names the slot and offers "Pick another time"
- **Brief:**
  - Steps: what you need (each offer with its "from" price in the visitor's currency, and the currency switch), where it is today, timing and budget, then about you.
  - "Your brief so far" builds as you answer.
  - Back and Continue move focus to the new step's heading; the sent state takes focus and is announced.
  - The choices are native radios drawn as pills, so arrow keys and form data work as standard.

### Integrations (server only, `lib/integrations/`)

- **Cal.com API v2:**
  - `GET /v2/slots` behind `GET /api/slots`
  - `POST /v2/bookings` behind `POST /api/bookings`
  - Cal.com sends the calendar invite.
- **Resend:** the brief is emailed to the studio inbox, with reply-to set to the sender.
- **Notion:** briefs and waitlist addresses become pages in two databases (the Privacy page names Notion). The database properties are in `.env.example`.
- Plain `fetch` calls; no SDKs.
- A service with no variables is off, and its form reports failure.
- A brief counts as sent once at least one of Notion and email has it, so it is never lost silently.
- `INTEGRATIONS=memory` fakes all three for tests and local runs. `/api/outbox` shows what they received, in that mode only.

### Brief and waitlist actions

- `sendBrief` is a Server Action that validates with Zod against the form's own options.
- The fields are offer, stage, timing, budget, name, email, company, message, how they heard, currency, UTM tags, referrer and landing page.
- There is a hidden honeypot for bots.
- `joinWaitlist` now stores through the same records service. The M3 placeholder store is gone.

### Analytics (Plausible)

- The script loads only when `NEXT_PUBLIC_PLAUSIBLE_DOMAIN` is set. It sets no cookies.
- All eight events from the handoff fire:
  - `price_card_click`
  - `offer_chosen`
  - `brief_started`
  - `brief_sent`
  - `call_booked`
  - `currency_changed`
  - `case_opened`
  - `waitlist_joined`
- One client component (`components/Analytics.tsx`) handles three sources:
  - clicks inside `[data-event]` elements
  - the kit's `kit:currency` and new `kit:capture` DOM events
  - case page views

  Pages add only attributes, no client code.
- The landing link's campaign tags and the referrer are kept for the session and sent with the brief.

### Kit

- `EmailCapture` dispatches `kit:capture` once an address is stored.
- `lib/analytics.ts` provides `track()` and the queue snippet, for any script with Plausible's call signature.

## Decisions and deviations

1. **Deck over appendix where both have the string:**
   - "Tell us what you are building." (appendix: "you're")
   - the lead
   - "Thanks. It is with us."

   The appendix supplies everything the deck lacks.
2. **Booking asks only for an email**, as on the board. Cal.com needs a name, so the address is sent as the name too.
3. **Day tiles follow the visitor's zone.** A visitor east of Lagos can see a late slot fall on the next day. Days with no free times are left out.
4. **No live currency conversion.** Brief prices come from `prices.ts`, like everywhere else.
